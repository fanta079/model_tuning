## 一、WSL2 安装与 VMware 共存

### 1. `wsl --install` 下载发行版报 `WININET_E_CANNOT_CONNECT`

- **原因**：微软 CDN 在国内连不上（WSL 本体已装好，只是发行版下不动）。
- **解法**：从国内镜像下载 `.wsl` 镜像，再手动导入：
  ```powershell
  wsl --import Ubuntu-24.04 E:\wsl\Ubuntu-24.04 .\ubuntu-24.04.5-wsl-amd64.wsl --version 2
  ```
- **镜像地址**：`https://mirrors.aliyun.com/ubuntu-releases/24.04/`（清华、中科大、华为云也有）。

### 2. 单线程下载只有几十 KB/s

- **原因**：镜像站对单连接限速。
- **解法**：分段多线程下载（8 连接并行，curl `-r start-end`），速度可提升 5~10 倍。

### 3. `wsl --import` 安装的发行版首次启动直接是 root

- **原因**：import 方式没有商店版的"创建用户"引导。
- **解法**：手动建用户并设为默认：
  ```bash
  adduser fanta && usermod -aG sudo fanta
  printf '[user]\ndefault=fanta\n' > /etc/wsl.conf
  # 然后 Windows 侧 wsl --shutdown 再进
  ```

### 4. WSL2 与 VMware 的 Hyper-V 冲突

- **根因**：CPU 的 VT-x 同一时刻只能被一个 Hypervisor 独占。
- **结论**：VMware Workstation 16.1+ 可以走 WHP 接口与 WSL2 共存，但**性能损失 8~15%**。
- **大坑**：开了 Hyper-V 后，VMware 虚拟机若勾选了「处理器 → 虚拟化 Intel VT-x/EPT」，**启动直接失败** —— 必须取消勾选。
- **建议**：VMware 17.x 起个人免费，对共存支持更成熟；macOS 虚拟机共存模式下无解。
- **兜底**：`toggle-hypervisor.bat`（管理员运行）可一键开关 Hyper-V，重启生效，操作完全可逆。

### 5. 每个 WSL 发行版必须单独一个目录

- 所有发行版的虚拟磁盘都叫 `ext4.vhdx`，同目录会互相覆盖。

## 二、网络与镜像

### 6. WSL 里 apt 只有 11k/s

- **排查顺序**：① Windows 代理（系统代理开关 / Clash 全局或 TUN 模式）→ ② IPv6 半残路由 → ③ 换镜像站。
- **测速命令**：
  ```bash
  curl -4 -o /dev/null --max-time 15 -r 0-10485759 -w "%{speed_download} B/s\n" https://mirrors.aliyun.com/ubuntu-releases/24.04/ubuntu-24.04.5-wsl-amd64.wsl
  ```
- **注意**：Ubuntu 24.04 的 apt 源是 **deb822 格式**，文件在 `/etc/apt/sources.list.d/ubuntu.sources`（不再是老的 sources.list）。

### 7. 国内必换的镜像清单

| 用途            | 镜像                                           |
| ------------- | -------------------------------------------- |
| apt           | `mirrors.aliyun.com` / `mirrors.ustc.edu.cn` |
| pip / uv      | `pypi.tuna.tsinghua.edu.cn/simple`           |
| PyTorch wheel | `mirrors.aliyun.com/pytorch-wheels/cu124`    |
| HuggingFace   | `export HF_ENDPOINT=https://hf-mirror.com`   |
| 模型/数据集        | ModelScope（国内直连最快）                           |

### 19. ⭐ hf-mirror 下大模型只有 ~0.4MB/s，魔搭快 27 倍

- **现象**：`WhisperModel('large-v3')` 预下载卡了很久，`model.bin` 3.1GB 几乎不动。
- **实测**（同一台机、同一时刻、各取前 30MB 测速）：
  | 源 | 速度 | 3.1GB 预计耗时 |
  |---|---|---|
  | `hf-mirror.com` | **0.4 MB/s** | ≈ 2 小时 |
  | `modelscope.cn` | **10.9 MB/s** | ≈ 5 分钟 |
- **结论**：**hf-mirror 只适合"小文件 / 少量权重"，上 GB 的模型一律先看魔搭有没有镜像。**
  魔搭上已验证存在：`Systran/faster-whisper-large-v3`、`Systran/faster-whisper-medium`、
  `pengzhendong/faster-whisper-large-v3-turbo`。探测仓库是否存在：
  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" \
    "https://www.modelscope.cn/api/v1/models/<组织>/<仓库>/repo/files?Revision=master"
  ```
- **解法**（不用装 modelscope，`curl -C -` 断点续传就够）：
  ```bash
  BASE=https://www.modelscope.cn/models/Systran/faster-whisper-large-v3/resolve/master
  for f in config.json preprocessor_config.json tokenizer.json vocabulary.json model.bin; do
      curl -L -C - --retry 5 -o "models/faster-whisper-large-v3/$f" "$BASE/$f"
  done
  ```
- **配套注意**：下到本地目录后要**按路径加载** `WhisperModel("/path/to/dir", ...)`；
  如果还传名字 `"large-v3"`，faster-whisper 会忽略本地目录、又回 HF 拉一遍。
  `setup_app.sh` / `run_app.sh` 已按这个规则处理（`WHISPER_SOURCE=modelscope` 默认）。
- **顺带纠正**：`setup_app.sh` 早先注释写"约 1.5GB"，那是 **medium** 的体积；
  **large-v3 是 3.1GB**，`large-v3-turbo` 才是 1.6GB。

## 三、Python 环境与依赖

### 8. `uv: command not found` 但明明装过

- **原因**：pipx 把 uv 装在 `~/.local/bin/`，当前终端的 PATH 没加载。
- **解法**：`export PATH="$HOME/.local/bin:$PATH"`（新终端会自动生效）；或激活 venv 后 `pip install uv` 装进环境。

### 9. `uv pip install unsloth` 会顺手升级 torch

- **现象**：装 Unsloth 时 torch 从 2.5.1+cu124 被升到 2.14.1+cu130。
- **教训**：装新库后先看 `uv pip list | grep torch`；**能跑就不要乱动版本**，驱动支持就没问题。

### 10. WSL 里绝对不要装 Linux 版 NVIDIA 驱动

- Windows 驱动会自动透传进 WSL，装 Linux 驱动会直接搞坏 CUDA 通道。

### 11. 微调框架是"两条路线"，按需安装

- **LLaMA-Factory**：WebUI + 配置文件，不写代码。
- **Unsloth**：Python 库，手写脚本，速度快 2x、显存省一半（对 8GB 卡是刚需）。
- 两者共用底层（Transformers/PEFT/TRL/bitsandbytes），按脚本选一条装即可。

## 四、数据与模型（本次最大的坑）

### 12. ⭐ Git LFS 指针文件：clone 下来的数据集只有 133 字节

- **现象**：`datasets` 加载报 `JSON parse error: Invalid value. in row 0`。
- **原因**：仓库用 Git LFS 管理大文件，本机没装 git-lfs，clone 下来的只是"取货单"（指针），不是文件本体。**而且这次 clone 把昨天完好的 18MB 真文件覆盖了**。
- **识别方法**：`head -c 100 文件`，看到 `version https://git-lfs.github.com/spec/v1` 就是指针。
- **解法**：
  ```bash
  # 根治（以后 clone 自动拉真实文件）：
  sudo apt install -y git-lfs && git lfs install
  # 或直接下直链（ModelScope 支持 /resolve/ 路径）：
  curl -L -o 文件名 "https://www.modelscope.cn/datasets/<组织>/<仓库>/resolve/master/<路径>"
  ```
- **验证**：指针对比 sha256 与 size，或直接用 Python `json.load` 试读。
- **教训**：clone 数据集到**新目录**，永远不要覆盖已有文件。

### 13. 模型放 `/mnt/e`（Windows 盘）加载慢

- **原因**：跨文件系统是 9P 协议，读取约 150MB/s（ext4 内可到 1GB/s+）。
- **影响**：8.8GB 模型加载 1~2 分钟，可接受；但**数据集和 checkpoint 频繁读写一定要放 Linux 家目录**。
- **注意**：WSL 的 vhdx 在 E 盘，把文件挪进 `~/` 依然不占 C 盘。

## 五、训练与显存（8GB 生存指南）

### 14. WDDM 显存税

- Windows 显示驱动模型预留 8~15% 显存：8GB 卡实际可用 ~6.8GB，Windows 桌面还要再占 ~1.3GB。**规划模型规模按 85 折算**。
- `.wslconfig` 里 `guiApplications=false` 可省 300~500MB。

### 15. 8GB 跑 4B QLoRA 的必备组合拳

`load_in_4bit`（权重 4bit）+ `use_gradient_checkpointing="unsloth"`（30% 速度换一半显存）+ `batch=1, accum=8` + `optim="adamw_8bit"` + LoRA 只训 0.1% 参数。

- OOM 了先关 Windows 端吃显存的程序（浏览器硬件加速），再把 `MAX_SEQ_LEN` 从 2048 降到 1024。

### 16. NVIDIA 控制面板的隐藏杀手

「CUDA - Sysmem Fallback Policy」要设为 **Prefer No Sysmem Fallback**。否则显存爆了不报错，而是静默把张量倒到内存走 PCIe —— 速度掉 10 倍还找不到原因。

### 17. 健康训练的体征
- loss 从 ~2.0 起步稳步下降；出现 `nan` 或恒为 0 就是有问题。
- `nvidia-smi` 显存吃满 7~~7.8GB、GPU 利用率 95~~100% = 正常。
- 训练过程**不需要网络**，全部本地计算。

### 18. ⭐ checkpoint 保存到 `/mnt/e` 时 torch.save 写 zip 损坏
- **现象**：训练跑完所有 step，最后在保存 `optimizer.pt` 时报 `RuntimeError: basic_ios::clear: iostream error` / `enforce fail ... unexpected pos ... vs ...`。
- **原因**：WSL 的 9P 文件系统对 `/mnt/e`（Windows 盘）上的 **ZIP 容器随机写**有已知 bug，`torch.save` 存优化器状态用 zip 格式会损坏。safetensors（顺序写）不受影响，所以 **LoRA adapter 往往已正常存好，丢的只是优化器状态**（微调不需要）。
- **识别**：看报错栈里是 `torch/serialization.py` 的 `_save` / `write_record` 且与 `optimizer.pt` 相关。
- **解法**：把输出目录改到 WSL 原生 ext4（如 `~/ft_outputs`），彻底避开 `/mnt/e`。在 `train_lora.py` 里：
  ```python
  OUTPUT_DIR = os.environ.get("OUTPUT_DIR", "/home/fanta/ft_outputs/qwen35-4b-lora")
  ```
  或在运行前 `export OUTPUT_DIR=/home/fanta/ft_outputs/qwen35-4b-lora`。训练完如需归档到 E 盘，用 `cp -r`（cp 不触发该 bug），别让 torch 直接写。
- **教训**：模型/数据**读** `/mnt/e` 没问题，但训练产物**写**要到 Linux 家目录。

## 六、GGUF 导出与推理（Qwen3.5 混合架构）

### 症状：GGUF 能跑，但输出全是字词乱码

```
> 我今天很累。
[Start thinking]
……嫌。只这个。问证据往包应付那样, value—不成消讲不担当。静一点。……
[ Prompt: 15.6 t/s | Generation: 5.0 t/s ]
```

**看着像中文，但语义完全崩塌，还混着英文碎片** —— 这不是 prompt 写错，也不是量化太狠，是**权重/计算图对不上**。

### 排查：先分清是"模型坏了"还是"转换坏了"

| 路径 | 结果 | 说明 |
|---|---|---|
| PyTorch + LoRA（`eval_persona.py`）| ✅ 回答正常、0 违规 | **模型本身没问题** |
| GGUF Q4_K_M（`llama-cli`）| ❌ 乱码 | 问题出在**转换或 llama.cpp 推理实现** |

这一步是决定性的：**同一份权重，PyTorch 正常、GGUF 乱码 → 不用怀疑数据和训练**。

### 根因：这个模型是"混合注意力 + MTP"，不是标准 Transformer

从 `config.json` 的 `text_config` 读出来的真实结构：

```
num_hidden_layers       : 32
layer_types             : linear_attention × 24 + full_attention × 8   (每 4 层 1 个全注意力)
num_nextn_predict_layers: 有（MTP 投机解码头）
```

而转出的 GGUF 里有 **33 个 block**（`blk.0` ~ `blk.32`）：

```
blk.0 .. blk.31   正常层（但其中 24 层是线性注意力）
blk.32            只有 nextn.eh_proj / enorm / hnorm / shared_head_norm
                  ← 这是 MTP 草稿头，不是普通层
```

**24/32 层是线性注意力** —— 只要 llama.cpp 对这套线性注意力递归状态的实现和 transformers 有偏差，这 24 层输出的就是噪音；剩下 8 层全注意力撑不住，句子就变成"有语法没语义"的字词汤。

> 对比：纯文本标准架构（Llama / Qwen2.5 等）转 GGUF 极少出这种事，因为路径被验证过成千上万次。**新架构 + 混合注意力 + 多模态，是 llama.cpp 支持最薄的一块。**

### 结论：别在这上面耗，换推理后端

| 方案 | 状态 |
|---|---|
| **PyTorch + GPU 4bit 直服**（`serve_hf.py`）| ✅ **采用** —— 和评测同一条加载路径，结果可信；4B 约 3.5GB 显存 |
| llama.cpp GGUF | ⏸ 搁置，等上游把 qwen35 线性注意力修稳 |
| 重编 CUDA 版 llama.cpp | ❌ 就算编了 CUDA，转换层的偏差还在，快而错没有意义 |

```bash
# 用这条代替 llama-server，接口完全一样（OpenAI 兼容）
source ~/venvs/ft/bin/activate
python serve_hf.py --adapter /home/fanta/ft_outputs/ev-v2/lora_adapter
```

### 顺带的经验

1. **`--jinja` 里出现 `[Start thinking]`**：说明模型开了思维链。人设数据里没有 thinking 段，推理时应关闭（`apply_chat_template(..., enable_thinking=False)`），否则它会先生成一堆无约束的"思考"。
2. **`convert_hf_to_gguf.py` 有 `--no-nextn / --no-mtp`**：可以排除 MTP 张量再转一次，用来验证是不是草稿头导致的。**但它是排除性实验，不是结论** —— 真正卡住的往往是线性注意力。
3. **`export_gguf.py` 这类"一条龙"脚本，中途失败要先验中间产物**：合并出来的 9.3GB HF 模型是完整的（索引声明 vs 实际字节只差 90KB 的 safetensors 头），**不需要重跑合并那 10 分钟**。

## 七、SFT 数据风格（v4 之后新增）

> 这一节的两个坑都不是"报错"，是**训练完了才发现说话变了**。共同点：SFT 学的是 token 分布，
> 你在数据里放什么比例，模型就输出什么比例 —— 跟提示词写得多好没关系。

### 20. ⭐ 模型每句都用「……」开头 —— 数据里 1/3 的回复就是这么开头的

- **现象**：不管问什么（"你好""为什么电脑变慢""帮我改句话"），她都拿「……」起头，
  最频繁的一条回复字面上就是「……嗯。」。
- **量化证据**（`rebuild_dataset.py` 的统计输出）：

  | 数据 | 回复轮次 | 均长 | 以「……」开头的占比 |
  |---|---|---|---|
  | ev3_all.json | 1231 | 16.9 字 | **36.4%** |
  | intro_api.json | 117 | 9.2 字 | **39.3%** |
  | help_api.json | 264 | 53.0 字 | 12.5% |
  | ev4_all.json（混合后） | 1495 | 23.3 字 | **32.2%** |

- **原因**：SFT 对**第一个 token** 的权重最高。三分之一的样本第一个 token 是「……」，
  模型就把"省略号开场"学成了默认动作。出现的重复回复（`……嗯。` 9 次）进一步加速了坍塌。
- **还有两个帮凶**：
  1. `help_pack.json` 的 6 条 few-shot 种子里有 **3 条自己就以「……」开头** —— 种子是生成器的
     风格标杆，标杆带病，产出必然带病。
  2. `gen_persona_data.py` 的硬性要求里，示例句子写的是「说『……行。』『随你。』」。
- **解法**（三道防线，缺一不可）：
  ```bash
  # ① 生成端：硬性要求加「开头一律不许用省略号」+ BAD_PATTERNS 加 ^…+ 直接判不合格
  # ② 种子端：清掉种子里所有开头的「……」，只留句中/句尾的
  # ③ 数据端：构建训练集时统一清洗，把一个可控比例（默认 8%）的省略号"放回去"
  python rebuild_dataset.py --src ... --keep-ellipsis 0.08
  ```
- **效果**：ev4 混合集「……」开头 32.2% → **2.9%**，均长同时从 23.3 → 22.5（省略号不算字）。
- **教训**：**省略号可以用，但不能当默认开场。** 清洗后要留 5%~10% 做变异，
  否则"从来不用省略号"又变成新的人为痕迹。

### 21. ⭐ 助手能力只占 17.7% 的轮次 —— 配比写了 40%，实际没人管

- **现象**：让她"解释一下""帮我排个计划"，她仍然只回半句话；v3 评测均长 22 → 16 字。
- **量化证据**：`help_pack.json` 里白纸黑字写着"建议 help 占 40%~50%"，但实际构建出来的
  ev4_all.json 里：

  | 来源 | 样本 | 回复轮次 | 轮次占比 |
  |---|---|---|---|
  | chat（纯闲聊，均长 16.9） | 880 | 1231 | **81.4%** |
  | help（能干活，均长 53.0） | 200 | 264 | **17.5%** |
  | intro（打招呼，均长 9.2） | 80 | 117 | 7.7% |

- **原因**：`cat a.json b.json` 式的合并只按**条数**堆，不按**轮次占比**配。闲聊数据量大、
  单条短，靠数量把长度分布和"回答方式"一起拖回去了。
- **解法**：`rebuild_dataset.py` 按 **assistant 轮次占比**重新采样各来源（不是按条数）：
  ```bash
  python rebuild_dataset.py \
      --src help=my_data/help_api.json+my_data/help_api_v2.json:0.50 \
      --src chat=my_data/ev3_all.json:0.42 \
      --src intro=my_data/intro_api.json:0.05 \
      --out my_data/ev5_all.json --keep-ellipsis 0.08
  ```
- **注意**：**改配比之前必须先扩数据**。help 只有 200 条时，按 50% 配比构建，脚本会为了
  维持比例把总量从 1088 条砍到 154 条（砍的是闲聊）—— 配比对了，数据没了。
  扩到 700 条左右，配比和总量才能同时成立。
- **教训**：**长度分布不能靠提示词救，只能靠数据配比救**。配比必须以"回复轮次"为单位算，
  按条数算一定会被短句作弊赢走。

### 22. ⭐ train_loss 不能跨数据集比较：0.76 和 2.09 可能是同一个水平

- **现象**：v4 训完 `train_loss = 0.760`，v5 训完 `train_loss = 2.087`，看起来像「v5 学崩了」。
- **真相**：loss 是**在各自训练集上**的平均交叉熵，数据集一变就没有可比性。三个因素都会把 loss 抬高：
  1. **回答变长**：v4 均长 23.3 字，v5 均长 36.8 字。token 越多，累积误差越大，逐 token 平均 loss 越高。
  2. **多样性变高**：v4 里 81% 是闲聊短句（「嗯。」「随你。」这类高频重复），模型很容易「背下来」，loss 自然压得低。v5 有 720 条覆盖 34 个场景的助手长回答，同一个问题有无数种合理答法，熵本来就高。
  3. **轮次数变多**：v5 是 2053 轮 / 1519 条，v4 是 1495 轮 / 1080 条。
- **正确判据**（按优先级）：
  1. **看曲线有没有平台**：v5 最后 8 个 log 点在 1.57~1.70 之间震荡，不再下降 → 这个数据量 + 这个步数已经收敛，不是训崩。
  2. **看实际输出**：能否讲清因果、长度是否配得上场合、开头是否还用「……」。
  3. **看 val loss / 评测集**——但本项目的 train_lora.py 没有 val 参数，只能用 `eval_persona.py` 跑固定题集对比。
- **反过来也成立**：loss 掉到 0.3 以下反而是**过拟合信号**（模型开始背训练集的原句），这时候应该减 epoch，而不是高兴。
- **教训**：换数据集的版本之间，**只比曲线形状和实际输出，不比 loss 绝对值**。

### 23. ⭐ 用训练集里的题验收 = 自欺：4 道验收题全部命中种子

- **现象**：v5 训完用「你好 / 为什么电脑越用越慢 / 三天内要交报告怎么安排 / 介绍一下你自己」验收，
  4 条里 3 条答得漂亮，一度以为「助手能力学到了」。
- **真相**：这 4 道题**全都在训练数据或生成种子里**：
  | 验收题 | 命中位置 |
  |---|---|
  | 你好 | `intro_pack.json` 种子「你好 → 嗯，在。怎么了。」 |
  | 三天内要交报告怎么安排 | `help_pack.json` 种子第 6 条，**题目一字不差** |
  | 介绍一下你自己 | `personas/haibara.md` 里写好的示例答案 |
  | 为什么电脑越用越慢 | `help_pack.json` 场景描述里的举例 + 种子第 1 条 |

  答得准说明它记住了，**不能说明它会答**。
- **唯一有信息量的是那道德偏离种子的题**：「为什么电脑越用越慢」没背种子（种子答的是「启动项堆太多」），
  而是自己组了「因为一直在装东西。先删……再关……最后装个监控工具」——把**「为什么」答成了「怎么办」**，
  没讲机制。这才是真实的短板。
- **验收题的正确写法**（必须与训练数据字面、语义都不重合）：
  - 换主语：电脑慢 → **手机越充越慢**
  - 换领域：报告排期 → **从零学做饭怎么开始**
  - 加约束：泛泛的「怎么选」→ **两份工作薪水差 30% 怎么选**
  - 带素材：**帮我把「你这个方案不行」改得客气点**
  - 测自述：**你能帮我做什么**
- **配套自检脚本思路**（3-gram Jaccard）：把验收题与 `personas/*.json` 的所有 user 轮做比对，
  相似度 >0.4 的题就作废。v5 生成数据与种子的重合率实测只有 0.2%，说明**数据本身没被种子污染**，
  是**测试题**选错了。
- **教训**：**能背下来的题不能用来验收。** 想验证「学到了能力」，题面必须落在训练分布之外。
