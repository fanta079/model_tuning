# P1 · E.V. 语音助手

> 最终形态：**安卓 App 的实时语音对话**。
> 本文档的 P1 是这个目标的第一版验证 —— 网页版、纯对话。
> 2026-10-18：语音链路已改成**真流式**（LLM 边生成 → 按句 TTS → 浏览器边收边播），不再是"憋完一整段再播"的对讲机。

---

## 一、P1 的范围（明确不做什么）

| 做 | 不做 |
|---|---|
| 你发语音 → 她回语音 | ❌ 工具调用 / agent 能力 |
| **流式**：边生成边合成边播（首声约 0.5~1.2s）| ❌ 端到端全双工（同一时刻真正边说边听，P5）|
| **可打断**：她在说时你开口 / 点球就停 | ❌ 向量记忆库（P2）|
| 网页界面 | ❌ 安卓 App（P4） |
| 简单的上下文（最近 12 条） | |

## 二、架构

```
浏览器（录音 / 播放）
      ↓ 音频
app/server.py（FastAPI，端口 8090）
      ├─ STT  faster-whisper (large-v3, int8_float16, CUDA)
      │       本地目录 models/faster-whisper-large-v3（魔搭下，不用 HF）
      ├─ LLM  serve_hf.py（E.V. LoRA · PyTorch 4bit，OpenAI 兼容，端口 8080）
      │       请求带 "stream": true -> 后端按 SSE 吐 token
      └─ TTS  edge-tts（音色见 app/voice.json），按句合成
      ↑ SSE 事件流：meta / delta / audio / done / error
```

> ⚠️ LLM 这一格**不是 llama-server**：Qwen3.5 是线性注意力混合架构，转 GGUF 输出乱码，
> 改用 `serve_hf.py`（PyTorch GPU 直服）。接口一模一样，`app/server.py` 零改动。
> 详见 `docs/踩坑记录.md` 第 18 条。

**三个组件互相独立**，谁没起会在界面右上角和 `/api/status` 里标出来，不会静默失败。

## 二·五、流式：一条回答是怎么"边说边出"的

### 时间轴（一条 3 句的回答）

```
t=0.0  用户说完 -> STT                    （whisper: 0.6~2s）
t=1.0  LLM 开始吐 token
t=1.3  第 1 句攒够标点 -> 立刻送给 edge-tts
t=1.7  第 1 句音频到浏览器 -> 开始播      ← 此时第 3 句还没生成
t=2.2  第 2 句音频 -> 无缝接上（预排期）
t=2.9  第 3 句音频
t=3.2  done（文字已全部到齐，音频还在播）
```

对比老版本：**要等 t=3.2 才开始合成，t=4.6 才出声**。所以流式不是"优化"，是体验的代差。

### 三个角色各做什么

| 角色 | 干什么 | 关键点 |
|---|---|---|
| `serve_hf.py` | `generate(stream=true)` 时返回 SSE，逐 token 吐 | `TextIteratorStreamer` + 后台线程；用户打断时 `StoppingCriteria` 让 generate 立刻停 |
| `app/server.py` | 收 token → **按句切** → 每句 TTS → SSE 推 `audio` 事件 | LLM 与 TTS **并行**（队列 + 有界背压），不等整段 |
| `app/index.html` | 逐字填气泡 + `decodeAudioData` 后**按时间轴预排期**播放 | 用 Web Audio `BufferSource`，不用 `<audio>` |

### 想调"多快开口"，只看这四个数

都在 `app/server.py` 顶部（都能用环境变量覆盖）：

| 变量 | 默认 | 作用 |
|---|---|---|
| `MIN_SEG` | 6 | 少于这么多字不单独切（"嗯。"单念很怪）|
| `MAX_SEG` | 42 | 一直没句号，最多攒这么长就硬切 |
| `EAGER_DELAY` | 0.55 | 首句等这么久还没句号 → 先切一段出声（优先切在逗号上）|
| `max_tokens` | 200 | 单轮上限 |

前端还有两个和打断有关的：`BARGE_LEVEL`（0.12）、`BARGE_HOLD`（0.25s）。

### 为什么段与段之间听不出接缝

- TTS 是**一句一段 mp3**，每段独立解码；
- 播放不是"播完再播下一段"（那样每段之间会有 100~300ms 空档），
  而是维护一个 `nextAt` 时间戳：`start(currentTime + max(0.04, nextAt - currentTime))`，
  下一段的起点 = 上一段的终点。JS 只是排期，真正的拼接由音频硬件时钟完成。

### 打断是怎么真的"停"下来的

```
你开口 / 点球
   -> 前端 AbortController.abort()      （停掉 fetch）
   -> 停掉所有已排期的 BufferSource    （立刻闭嘴）
   -> 后端 generator 被取消 -> worker 收到 CancelledError
   -> 释放 _LLM_LOCK + 已生成的部分写进历史
   -> serve_hf 侧的连接断开 -> StoppingCriteria 触发 -> generate 停止（不白烧显存）
```

`_LLM_LOCK` 是 `Semaphore(1)`：8GB 卡只够一份 4B，打断后旧请求可能还没退干净，
新的一轮必须等它真正退出，否则两个 KV cache 直接把显存顶爆。

### 三个已知坑（都已处理）

| 现象 | 原因 | 处理 |
|---|---|---|
| 音频段之间"咔"一下 | 用 `<audio>` 逐段播会重新缓冲 | 改 Web Audio 预排期 |
| 偶发乱码方块 | Qwen 是字节级 BPE，单个 token 可能是半个汉字 | `serve_hf.py` 里遇到 `\ufffd` 先攒着，等补齐再发 |
| 打断后模型还在生成 | 只断了前端，后端 generate 跑到底 | `StoppingCriteria` + 连接断开检测 |

> 顺带一个**不要走的路**：MSE（MediaSource）播 mp3 在 Chrome 能跑、Firefox 直接不支持，
> 而且延迟反而更高。要"低延迟 + 无缝"，Web Audio 的 BufferSource 才是正解。

## 三、跑起来
```bash
# ① 建环境（独立 venv，不碰训练环境 ~/venvs/ft）
bash setup_app.sh            # 含预下载 whisper 模型（large-v3 约 3.1GB，走魔搭）

# ② 另开一个终端，起模型服务（在【训练环境】里）
source ~/venvs/ft/bin/activate
python serve_hf.py --adapter ~/ft_outputs/ev-v2/lora_adapter

# ③ 起助手（回到 evapp 环境）
bash run_app.sh
# 浏览器打开 http://localhost:8090
```

`run_app.sh` 会自动发现 `models/faster-whisper-*` 并按路径加载；
**别手动传模型名** `large-v3`，那会忽略本地目录、又回 HF 重下一遍。

**临时用别的模型也行**：`LLM_BASE=http://127.0.0.1:8080/v1 bash run_app.sh`

初版为了 HUD 质感把「说明文字」压到 9px + `rgba(...,.22)`，实测**基本读不清**：

| 元素 | 改前 | 改后 | 对比度 |
|---|---|---|---|
| 提示行 `#hint` | 9.5px / .44 | 12.5px 无字距 / .74 | 3.28 → **8.24 : 1** |
| 顶栏组件状态 `#health` | 9px / .22 | 10.5px / .74 | 1.63 → **8.24 : 1** |
| 分区标题 `.sec` | 9px / .22 | 10px / .74 | 1.63 → 8.24 |
| 对话正文 `.bub` | 12.5px | 13.5px | **16 : 1** |
| 系统消息 | 10px / .22 | 12px / .74 | 1.63 → 8.24 |

另外补了 `::selection`（暗底上浏览器默认选中色几乎看不见，选字很费劲）。

## 三·五、电话模式（连续对话，不用按键）

界面右侧有个「**电话**」按钮。点开之后：

```
你说 → 停顿 1.4 秒 → 自动发送 → 她**边说边出**地回答 → 说完自动重新收音 → 你接着说……
```

**全程不用碰按钮**，就是打电话的感觉。再点一下「挂断」退出。

### 它怎么知道你说完了

不是靠按键，是靠**音量**（VAD，语音活动检测）：

| 判断 | PC 预设 | 手机预设 | 含义 |
|---|---|---|---|
| 开始说话 | 电平 > `0.055` | > `0.10` | 这一轮有人声了（手机 AGC 抬高底噪）|
| 说完了 | 静音 **1.4 秒** | **1.2 秒** | 自动切句发送（宁长勿短）|
| 太短的当噪声 | < **0.35 秒** | < **0.40 秒** | 咳嗽/碰麦/鼠标声直接丢 |
| 打断她 | > `0.12` 持续 0.25s | > `0.24` 持续 0.40s | 手机扬声器回声大，必须抬高 |
| 她说完到重新收音 | 260ms | 520ms | 防尾音被当成你说话 |
| 单轮上限 | **20 秒** | **20 秒** | 防止一口气录太长 |

**为什么手机必须另一套**：手机上扬声器和麦克风贴在一起，她的声音会直接进麦克风；
系统 AGC 又会把底噪一起抬起来。用 PC 的阈值，症状固定是两种 ——
「她还没说完就被自己的回声打断」和「你还没说完就被切成发送」。

设备靠 UA + `pointer:coarse` 自动判断；排查时可强制覆盖：

```
http://<地址>/?gain=mobile     强制手机预设（在 PC 上模拟）
http://<地址>/?gain=pc         强制 PC 预设
```

电话模式启动时，舞台上那行「输入设备：…」后面会标出当前用的是哪套预设。

参数都在 `app/index.html` 顶部的常量里，嫌它太灵敏/太迟钝就改：

```js
const VAD_SPEECH = 0.055;   // 调大 → 更难触发（环境吵时用）
const VAD_SILENCE = 1.4;    // 调大 → 等更久才认为你说完
```

### 可以打断她

她正在说的时候，你直接开口：

- 麦克风持续监测，电平 > `0.12` 且持续 **0.25 秒** → **停掉播放 + 掐掉还在合的 TTS，立刻切成收音**
- 阈值比 VAD 高，是为了不被扬声器的回声误触发（戴耳机更稳）
- 因为音频是流式排期的，打断能做到"当场闭嘴"，剩余音频段和没生成的 token 一起作废

### 实现要点（为什么能同时"录"和"听"）

永远用**两个独立的 AnalyserNode**：

```
麦克风        → micAnalyser      （负责 VAD + 打断判断）
TTS BufferSrc → player.an        （负责让球体跟着她的声音跳）
```

两者必须分开 —— 否则她说话时你就"听不见"自己在打断。
流式版本里这个要求更强了：**播放侧的 analyser 必须独立于播放排期**，
不能像老版本那样"每轮重建一个 `<audio>` 再挂上去"。

## 四、音色（这一块必须单独调）

默认 TTS 音色是"通用客服女声"——温柔饱满有起伏；E.V. 是冷淡克制话少。
**不处理的话，就是热情小姐姐在念冷淡台词。**

### 三个旋钮（edge-tts 能控制的全部）

| 旋钮 | 往哪拧 | 听感 |
|---|---|---|
| `voice` | 换底子 | 不同音色基础 |
| `rate` | **负值** | 更慢 → 显得不在乎 |
| `pitch` | **负值** | 更低 → 显得冷 |

### 怎么选

```bash
python app/try_voices.py        # 生成 8 组候选 + 可点击播放的网页
# 打开 app/voice_samples/index.html 听完，把选中的填进 app/voice.json
```

### "声色"其实是 5 个维度

| 维度 | 由什么决定 | edge-tts 能控吗 |
|---|---|---|
| **音色（底色）** | 声带、共鸣腔 —— "是谁" | ✅ `voice` |
| **音调** | 基频高低 | ✅ `pitch` |
| **语速** | 说话快慢 | ✅ `rate` |
| **节奏与停顿** | 断句、气口 | ⚠️ 只能靠标点间接影响 |
| **语气 / 情绪** | 冷淡 vs 热情 | ❌ **控不了** |

**所以 edge-tts 能做到"冷"（低音调 + 慢语速），做不到"克制的疲惫感"** —— 那属于第 5 维，必须换实现。

### 三个层级

| 层级 | 做法 | 需要什么 | 像的程度 | 状态 |
|---|---|---|---|---|
| **① 选 + 调** | 换现成音色底子 + 拧 rate/pitch | 无 | 30~50% | ✅ **现在在这层** |
| **② zero-shot 克隆** | 给 3~10 秒参考音频，模型提取音色 | 一段干净音频 | 70~90% | 待做 |
| **③ 少样本微调** | 1~5 分钟音频 + 训练一轮 | 音频 + 训练 | 90%+ | 待做 |

**② 是性价比最高的一层** —— 不用训练。

### ② 的参考音频要求（5 条，决定成败）

| 要求 | 原因 |
|---|---|
| **干净**（无背景音/音乐/混响）| 噪音会被当成音色的一部分学进去 |
| **情绪中性**（别用大笑/哭腔）| 情绪会被固化成音色的"默认状态" |
| **3~10 秒连续独白** | 不要拼接碎片，拼接会有"拼接感" |
| **单人** | 多说话人会串音 |
| **≥16kHz 采样** | 太低会抹掉音色细节 |

工具：**CosyVoice 2**（阿里）/ **IndexTTS**，中文强且支持 zero-shot。

### ⚠️ 真正难的不是"像"，是"稳"

zero-shot 克隆最常见的问题**不是不像，而是同一段话里音色在飘**：

| 现象 | 原因 |
|---|---|
| 短句音色飘 | 音频太短，音色特征提取不足 |
| 一激动就变声 | 模型跟着情绪走，忘了"要像谁" |
| 每句听起来都不一样 | 参考音频质量差 |

**"保证声色差不多"的敌人其实是「一致性」，不是「相似度」。**

对策：
- 参考音频**宁可短，但要干净**（3~5 秒足够）
- 选支持**音色缓存**的实现（存 voice embedding，每句复用而非重新提取）
- 别处理太长太激动的句子 —— **E.V. 话本来就短，天然占便宜**

### ⚠️ 版权红线

**不能克隆灰原哀原版配音（林原惠）的音色** —— 明确侵权。

可用的参考音频：**自己的声音** / 授权可商用的音色 / 找配音的人专门录一段。

### 换实现只改一处

TTS 抽成了独立函数 `tts()`（`app/server.py`）。从 edge-tts 换到 CosyVoice / Piper，**只改这一个函数**，其余代码零改动。

### 顺序建议

```
① 用 edge-tts 跑通 P1 → 试听选音色 → 定下【方向】（冷到什么程度/多慢/多低）
        ↓
② 记下参数（如 rate -15% / pitch -15Hz）
        ↓
③ P3 上克隆方案时，拿这个方向去【挑参考音频】（找同样冷、同样语速的人声）
```

**方向定了，换实现才好对齐。** 否则会在"试各种 TTS"上耗掉大量时间，而其实你要的只是"再冷一点、再慢一点"。

### 开源 TTS 候选（2026-10 调研，按 8GB 卡筛过）

先摆清楚一个事实：**"贾维斯 / Friday 的原声"不存在开源版，也不该有** ——
那是 Paul Bettany / Kerry Condon 的声音，谁把权重打包卖都是侵权。
能拿到的是**同气质**：英式、低音、慢、平、句尾下沉。

| 方案 | 规模 | 中文 | 流式 | 克隆 / 造音色 | 协议 | 8GB 卡 |
|---|---|---|---|---|---|---|
| **Qwen3-TTS** 0.6B / 1.7B | 0.6B / 1.7B | 好（10 语）| ✅ 首包 ~97ms | ✅ 3s 克隆 + **文字造音色**（VoiceDesign）| Apache-2.0 | 0.6B ~4GB ✅ |
| **Chatterbox** Multilingual | 0.5B | 一般（23 语）| ❌ 整段生成 | ✅ 5s 克隆 + **exaggeration 调情绪** | MIT | ~6-7GB ⚠️ |
| **GPT-SoVITS** v2ProPlus | ~0.2B | **最强**（含粤语）| 一般 | ✅ 5s 零样本 + 1min 微调 | MIT | 很小 ✅ RTF 0.028 |
| **CosyVoice 2/3** | 0.5B | 强（18+ 方言）| ✅ 首包 ~150ms | ✅ 3s 克隆 + 指令控风格 | Apache-2.0 | ~4GB ✅ |
| **Kokoro-82M** | 82M | 一般 | CPU 实时 | ❌ 只有 54 个预置音色 | Apache-2.0 | 几乎不占 ✅ |
| IndexTTS2 | — | 强 + 情绪最好 | 一般 | ✅ | B站协议，商用需问 | **~8GB** ❌ |

**结论（针对本项目）**

1. **想"造"一个 Jarvis/Friday 式的音色** → Qwen3-TTS 0.6B 的 VoiceDesign：
   提示词写「四十岁上下的英国管家，中低音，语速平稳，语气克制，句尾下沉，不带笑意」。
   不参考任何真人，法律最干净。**这是最贴合"必须这个音色"的路。**
2. **想要 E.V. 那股"冷淡到平"** → Chatterbox 的 `exaggeration=0.25~0.3`（默认 0.5，越高越夸张）。
   唯一的连续情绪旋钮，正好用来把"热情"拧掉。代价：不支持流式，中文不如国产模型。
3. **想要"最像、最稳、以后不再折腾"** → GPT-SoVITS：找一段合法录音（自己录 / 请人录 1 分钟），
   微调一轮，之后音色不飘；4060Ti 上 RTF 0.028，比实时快 35 倍。
4. **想马上听个响** → Kokoro 自带的英式音色（`bm_george` 男 / `bf_isabella` 女），
   十分钟就能判断"英式管家感"够不够，再决定要不要上大模型。

⚠️ 显存现实：现在 `serve_hf`(3.4GB) + whisper large-v3(1.6GB) ≈ 5GB，TTS 只剩 ~2.5GB。
想上 Qwen3-TTS 1.7B / IndexTTS2 / Chatterbox，得先把 whisper 换成 `large-v3-turbo`（省 ~1.4GB），
或者把 TTS 单独起服务、**按需加载用完就卸**。

### 造音色的工具已经写好了：`app/design_voice.py`

```bash
bash setup_tts.sh                           # ① 建 ~/venvs/tts + 下 4.5GB 权重（魔搭）
source ~/venvs/tts/bin/activate

python app/design_voice.py --only 1,3,4     # ④ 生成候选 + app/voice_samples/design/index.html
python app/design_voice.py --lock 3         # ⑤ 锁定成 app/voice_lock/ref.wav，写进 voice.json
```

**为什么是第三个 venv**：`qwen-tts` 会拉自己的 torch/transformers。
装进 `~/venvs/ft` 会动到训练环境，装进 `~/venvs/evapp` 会破坏 faster-whisper 依赖的那份 cu12 运行库
（`run_app.sh` 拼的 `LD_LIBRARY_PATH`）。所以单独建 `~/venvs/tts`，不用了整个删掉也不影响主链路。

8 条基础候选覆盖「冷淡女管家 / 深冷电台 / 清冷少女 / 中性系统音 / 温柔但疏离 / 低哑克制」
+ 2 条英文对照（英式男管家、英式女助理）；
另有 5 条**少女感细分**（9~13：更冷 / 毒舌 / 低哑 / 中性化 / 软底冷调），
全部以 3 号为基准、一次只动一个变量 —— 这样才知道到底是哪个词在起作用。

**描述词的写法（照这个结构改就行）**：
`性别 + 年龄 → 音高 → 语速 → 句尾走向 → 情绪态度`
例：「成年女性，三十岁上下，中低音，语速平稳偏慢，**句尾持平不上扬**，语气克制疏离，没有笑意。」

> 句尾上扬 = 亲切。**冷感十有八九输在这一句上。**

锁定的意义：VoiceDesign 每次生成都会微调音色，**同一段描述重跑也不会完全一样**。
`--lock` 就是把某一遍的输出冻成参考音频，之后改用 0.6B Base 做 voice clone
（`create_voice_clone_prompt(ref_audio=..., ref_text=...)`），每句音色一致，显存只要 ~2GB。

### 接进主链路：`app/tts_server.py`（已接好，待实测）

```
server.py 的 tts()  ──HTTP──>  app/tts_server.py  ──Qwen3-TTS 0.6B──>  ref.wav（clone prompt）
```

| 环境变量 | 效果 |
|---|---|
| 不设 `TTS_BASE` | 走 edge-tts，行为和以前完全一样 |
| `TTS_BASE=http://127.0.0.1:8092` | 走本地克隆服务；`/api/status` 会真的探活，挂了显示 × |

```bash
bash setup_tts.sh --only base      # 只补 0.6B Base（1.5GB）
python app/tts_server.py --check   # 念一句，存成 app/voice_lock/check.wav —— 先确认是她的声音
python app/tts_server.py           # 常驻 :8092
TTS_BASE=http://127.0.0.1:8092 bash start_ev.sh
```

**为什么是独立进程而不是在 `server.py` 里加载模型**：
显存独立核算、模型只加载一次、换音色只重启它；它挂了对话主链路照常（只是没声音）。
返回的是 **wav**（不是 mp3）—— 前端用 `decodeAudioData` 解码，格式无所谓，wav 还省一层编码。

显存账：LLM 3.4 + whisper 1.6 + TTS 2.0 ≈ **7GB**，8GB 卡贴着上限。
真 OOM 就把 STT 挪 CPU（`WHISPER_DEVICE=cpu WHISPER_MODEL=…-turbo`），别去动模型侧。
更省事的做法是直接 `bash start_ev.sh --tts`，脚本会自己把 STT 挪到 CPU 再起。

### 两个后处理，默认都开

克隆会把参考音频的**坏毛病一起复制**，实测两条必须修：

| 问题 | 实测 | 处理 | 开关 |
|---|---|---|---|
| 开头空 1.2 秒 | 8 字短句前面 1190ms 静音（参考只有 30ms） | 剪首尾，留 40ms 头 / 60ms 尾 | `TTS_TRIM=0` 关 |
| 句中 800ms 长停顿 | 两个 840ms 停顿，8 个字的句子占 2.66 秒 | >=600ms 的压到 400ms，短的保留 | `TTS_GAP=0` 关 |

不剪首尾的话，`server.py` 是**按句切分逐句推**的，每句 1.2 秒空白 = 三句话 3.6 秒死气。
压缩停顿同理：单句有停顿有味道，连成一段就是卡顿。目标值 400ms 是刻意的——
比 320ms 松一点，还听得见"顿一下"，但不会拖。

**参考音频决定上限，别忽略**：`ref.wav` 里 6 处 500~1140ms 停顿，克隆出来必然也带停顿。
想更好听，换一条 5~7 秒、语速均匀、无长停顿的参考（`--ref` + `--ref-text` 可 A/B，不动 voice.json）。
`--ref-text` 必须与音频逐字一致，否则音色会漂。

> 2026-10-18 结论：0.6B 克隆对比 VoiceDesign 原声（3 号）"差不了多少"，**就用 0.6B**。
> 1.7B Base 保真度更高但要 3.4GB，和 LLM 挤不下 8GB，不值得。

## 六、已知限制

- **模型跑在 PC 上** → 安卓 App 要连局域网，PC 得常开
- **语音识别和合成也在 PC 上** → 延迟 = 网络 + STT + LLM + TTS；界面会显示 **首声** 和 **总时长**
- **edge-tts 每句一次网络往返（约 200~400ms）** → 她话越短、句子切得越碎，"生成速度"越容易跟不上"播放速度"，
  中间会出现小停顿。想更连贯就把 `MIN_SEG` 调大（句子更长、更少、更顺），代价是首声变慢
- **显存账（8GB 卡）**：`serve_hf`（4B 4bit + KV）≈ **3.4GB**，whisper large-v3 int8_float16 ≈ **1.6GB**，合计 ≈ **5GB** ✅
- ⚠️ **但训练和语音助手不能并发**：`train_lora.py` 峰值 ≈ 6.5~7.5GB，两者相加 10GB+，8GB 必 OOM
  - 训练前：`pkill -f serve_hf.py`
  - 训练后：重启 `serve_hf.py`（它**启动时**才加载 adapter，训练完不重启还是旧权重）
  - 想边训边聊只能把对话模型放 CPU（3~8 tok/s，基本没法用）
- 磁盘：whisper large-v3 = 3.1GB；嫌大换 `large-v3-turbo`（1.6GB，CPU 上快约 4 倍）
- edge-tts 需要联网（微软的免费接口）

### ⚠️ 状态机：同一个按钮 / 球，不同状态含义不同

第一版写的是 `mic.disabled = (state !== 'idle')`，结果**一点「说话」按钮就变灰**，永远发不出去。

原因：同一个按钮承担了**多个动作** ——

| 状态 | 这一下点下去的意思是 |
|---|---|
| `idle` | 开始录音 |
| `recording` | **停止录音并发出去** ← 就是「发送」 |
| `thinking` / `speaking` | **打断她，并立刻开始收音** ← 流式之后才有的第三义 |

```js
mic.disabled = !hasMic || phoneOn || micBlocked;   // 只有"没有麦/电话模式/组件没就绪"才禁用
```

> 一行逻辑错误，现象却是"麦克风有问题" —— 这种最容易误判成权限/驱动问题。
> 以后调这类带状态机的 UI，**先把状态 × 可用性列成表格**，比盯着报错有效。

### ⚠️ 麦克风只在「安全上下文」可用（实测踩过）

浏览器不是有麦克风就给，而是**只给安全上下文**：

| 你打开的地址 | `navigator.mediaDevices` | 能录音吗 |
|---|---|---|
| `http://localhost:8090` | 有 | ✅ |
| `http://127.0.0.1:8090` | 有 | ✅ |
| `http://172.22.x.x:8090`（局域网 IP）| **undefined** | ❌ 报 `Cannot read properties of undefined (reading 'getUserMedia')` |
| `file:///.../index.html`（双击打开）| **undefined** | ❌ 同上 |

**所以本机测试必须用 `localhost`，不能用网卡 IP。**
`127.0.0.1` 和 `localhost` 被浏览器特批为安全上下文，其它 http 一律不算。

**已做的三处兜底**

1. 页面会自己判断并说明原因（区分 file:// / 非安全上下文 / 浏览器不支持）
2. **打字入口**：麦克风不可用时，输入框照常可用 —— 跳过 STT，直接 LLM → TTS，**回复仍然有声音**
3. `/api/status` 不再阻塞地加载 whisper —— 否则模型载入那 10~20 秒里按钮会一直「准备中」，看着像坏了

> 手机 / 局域网要用麦克风，只有两条路：**HTTPS**（自签证书或内网穿透），
> 或者**安卓原生 App**（系统级权限，不受安全上下文限制 —— 这正是 P4 的方案，见第五节的说明）。

### ⚠️ 还有一层：WSL2 的 NAT（手机连不上的真正原因）

就算解决了 https，还有一道墙：**服务跑在 WSL2 里，WSL2 有自己的 NAT**。

```
手机 ──> 192.168.3.205:8090（Windows 网卡）  ──?──>  172.22.48.x:8090（WSL）
```

`localhost` 能通是因为 `.wslconfig` 里的 `localhostForwarding=true` —— 它**只对本机生效**。
手机访问 Windows 的 192.168.3.205 时，Windows 上没有任何进程在听，直接 connection refused。

两种打通方式：

| 方式 | 操作 | 代价 |
|---|---|---|
| **portproxy**（兼容性最好）| `windows/expose-wsl.ps1`（管理员运行）| `wsl --shutdown` 后 WSL IP 会变，**要重跑** |
| **mirrored 网络**（Win11 + WSL 2.0+）| `.wslconfig` 的 `[wsl2]` 加 `networkingMode=mirrored` → `wsl --shutdown` | 一次性，之后 WSL 直接用宿主网卡 |

> 另外：`tts_server.py` 默认绑 `127.0.0.1`，**不需要**暴露 —— 它只被同机上的 `server.py` 调。
> 要暴露的只有 `8090`。

### 手机方案选型（结论）

| 方案 | 家里 | 外面 | 依赖 | 一次性成本 | 维护 |
|---|---|---|---|---|---|
| **tailscale + PWA** ✅ | 直连 | 走中继 | 境外控制面 | 手机装 App、授权一次 | 低（IP 变了也不用改）|
| 自签证书 + 局域网 | 延迟最低 | ❌ | **零外网依赖** | 手机装一次 CA + 解决 WSL NAT | 中 |
| WebView 壳 APK | ✅ | ✅（同一 WiFi）| 无 | Android Studio ~10GB + 签名 | **高**：改 UI 就要重打包 |
| cloudflared 临时隧道 | ✅ | ✅ | Cloudflare | 装二进制 | 高：域名每次重启都换 |

**推荐主线：tailscale + PWA。** 一个方案同时干掉两个阻塞（跨网络可达 + https），
还顺手绕过 WSL 的 NAT；装完 https，浏览器「添加到主屏幕」就是全屏 App。

**备选：自签证书 + 局域网**（`make_tls_cert.sh` 已就绪）。适合"只在家的 WiFi 里用"，
零外网依赖、延迟最低，代价是手机装一次 CA。

**什么时候才值得做 APK**：只有两种需求会让 PWA 不够用 ——
① 锁屏 / 后台也能叫醒她（PWA 切后台 AudioContext 会被挂起）；
② 要常驻通知或悬浮球。除此之外 WebView 壳只是"把网页塞进 App"，能力并不比 PWA 多。

> 安卓上装 PWA 请用 **Chrome / Edge**；国产自带浏览器多数不支持完整的"添加到主屏幕"。
