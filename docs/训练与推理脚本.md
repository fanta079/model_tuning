## 一、所有脚本共享的三个前提

### 1. 必须在 WSL 内跑

Unsloth 不支持原生 Windows。所有命令前面都要：

```bash
source ~/venvs/ft/bin/activate
```

> Unsloth **不在一键环境脚本里**，环境重建后要单独 `uv pip install unsloth`。

### 2. 三个"全脚本通用"的坑已在代码里处理

| 坑 | 表现 | 代码里的解法 |
|---|---|---|
| Qwen3.5 是多模态模型 | `from_pretrained` 返回的是 **Processor** 而非 tokenizer，直接 `tok(text)` 会把文本当图片解码 | `tok = getattr(tokenizer, "tokenizer", tokenizer)` |
| 不会在 `<|im_end|>` 停 | 答完继续编下一轮 `user/assistant` | 显式 `eos_token_id=[<|im_end|>, <|endoftext|>]` + `STOP_MARKS` 兜底截断 |
| 默认输出思考链 | 回答前先吐一段 `<think>` | `apply_chat_template(..., enable_thinking=False)`（模板不支持时 try/except 回退） |

这三条在每个推理脚本里都重复出现了，**自己写新脚本可以直接抄**。

### 3. 训练产物不要写 `/mnt/e`

`/mnt/e` 是 9P 文件系统，`torch.save` 写 zip 会损坏。所以 `OUTPUT_DIR` 默认是 WSL 原生目录
`/home/fanta/ft_outputs/...`，训练完再把 `lora_adapter` 拷回 E 盘归档。

## 二、`train_lora.py` —— 唯一真正训练的脚本

> 零基础读者先看 [train_lora 脚本导读](./train_lora脚本导读.md) —— 那篇逐个名词拆讲（SFTTrainer、LoRA、packing、-100 掩码等），本篇偏速查与操作。

172 行，串完 5 步：**4bit 加载 → 挂 LoRA → 数据渲染成 text → SFTTrainer → 存 adapter**。

### 2.1 环境变量（全部通过环境变量控制，不改代码）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `BASE` | `/mnt/e/VMOS_workspace/model_tuning` | 项目根 |
| `MODEL_PATH` | `models/Qwen3.5-4B` | 底座目录（BF16 safetensors） |
| `DATA_PATH` | `alpaca_zh/alpaca_data_zh_51k.json` | 换成你的 train.json |
| `OUTPUT_DIR` | `/home/fanta/ft_outputs/qwen35-4b-lora` | **每训一版换个版本号**，别覆盖旧 adapter |
| `DATA_FORMAT` | `alpaca` | `alpaca` 单轮 / `chat` 多轮 |
| `SYSTEM` | 空 | 多轮时统一注入的 system 人设 |
| `RESPONSES_ONLY` | `0` | `1` = 只对 assistant 回复算 loss |
| `NUM_EPOCHS` | `1` | 训练轮数 |
| `SMOKE_TEST` | `1` | ⚠️ **默认只跑 500 条**，全量要显式 `SMOKE_TEST=0` |

`MAX_SEQ_LEN` 是代码里的常量（2048），要改得动文件。

### 2.2 两种数据格式

**A. Alpaca 单轮**（通用指令，`DATA_FORMAT=alpaca`）

```json
{"instruction": "用简单的话解释通货膨胀", "input": "", "output": "..."}
```

渲染逻辑：`instruction + "\n" + input` 拼成一条 user 消息，`output` 作 assistant。
**不注入 system**（alpaca 数据本身没有 system，硬加会破坏分布）。

**B. Chat 多轮**（人设 / 客服，`DATA_FORMAT=chat`）

```json
{"conversations": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]}
```

整段用 `apply_chat_template` 渲染成一条 `text`；若给了 `SYSTEM` 且数据里没有 system，会自动加在最前面。

> ⚠️ **多轮人设必须配 `RESPONSES_ONLY=1`**。否则模型会连"用户说的话"一起学 ——
> 数据里用户的语气会污染人设，且 loss 被大量用户 token 稀释。

### 2.3 超参逐条解释（8GB 视角）

| 参数 | 值 | 为什么 |
|---|---|---|
| `load_in_4bit` | True | 4B BF16 要 8.8GB，4bit 压到 ~2.6GB，8GB 卡唯一选择 |
| `max_seq_length` | 2048 | 4B + 2048 + batch1 刚好不爆；爆了就降 1024 |
| `r / lora_alpha` | 16 / 32 | alpha/r = 2 是常用起点。r 越大表达力越强、adapter 越大，人设任务 16 够 |
| `target_modules` | q,k,v,o + gate,up,down | 注意力 + FFN 全覆盖。只挂 q,v 效果弱很多 |
| `lora_dropout` | 0 | 数据量不大时 dropout 反而拖慢收敛，Unsloth 也推荐 0 |
| `use_gradient_checkpointing` | `"unsloth"` | 用重算换显存，是 8GB 能开 2048 的关键 |
| `per_device_train_batch_size × grad_accum` | 1 × 8 | 显存只跟 1 有关，等效 batch 8 保证梯度稳定 |
| `learning_rate` | 2e-4 | LoRA 专用区间（全参训练才用 1e-5 量级） |
| `num_train_epochs` | 1（人设建议 3~5） | 数据少（几百条）必须多跑几轮；51k 通用数据 1 轮就够 |
| `packing` | True | 把短样本拼满 2048，吞吐提升明显。人设数据都很短，收益最大 |
| `optim` | `adamw_8bit` | 8bit 优化器状态，省显存 |
| `save_steps` | 500 | 步数少于 500 的训练中途不存 checkpoint，靠最后 `save_pretrained` |

> **步数怎么估**：`steps = 样本数 × epochs ÷ 8`。
> 例：ev-v1 用 361 条、3 轮 → 约 138 步，和 `checkpoint-138` 对得上。
> 实际耗时看日志里的 `it/s`，`总步数 ÷ it/s` 就是大致秒数。

### 2.4 `RESPONSES_ONLY` 到底做了什么

```python
train_on_responses_only(
    trainer,
    instruction_part="<|im_start|>user\n",
    response_part="<|im_start|>assistant\n",
)
```

它遍历每条样本的 label，把 **user 段（含 system）全部置成 `-100`**，loss 只统计 assistant 段。
效果：损失信号 100% 来自"该怎么说"，不带"该听什么"。

人设 / 风格 / 客服这三类任务都应该开；纯指令跟随（alpaca）可以不开。

### 2.5 训练前的标准动作：先冒烟

```bash
# 1) 不看数据、不烧卡，先跑 500 条 8 步左右，确认能训起来
python train_lora.py

# 2) 冒烟通过再全量
SMOKE_TEST=0 python train_lora.py
```

冒烟只看三件事：数据条数打印对不对、loss 是不是从 3~5 开始往下走、有没有 OOM。

### 2.6 一条完整的多轮人设训练命令

```bash
source ~/venvs/ft/bin/activate

DATA_PATH=/mnt/e/VMOS_workspace/model_tuning/my_data/ev3/train.json \
DATA_FORMAT=chat RESPONSES_ONLY=1 NUM_EPOCHS=5 \
OUTPUT_DIR=/home/fanta/ft_outputs/ev-v3 SMOKE_TEST=0 \
nohup python train_lora.py > ~/train_ev_v3.log 2>&1 &

tail -f ~/train_ev_v3.log          # 另开终端看 loss
```

几个容易忘的点：

- `OUTPUT_DIR` **必须换版本号**。同名会续写旧目录，出问题时说不清是哪一版
- `nohup ... &` 是必须的，SSH/终端断了训练不会死
- 日志重定向到 `~/`（ext4），别写 `/mnt/e`
- 想中途停：`pkill -f train_lora.py`，已存的 `checkpoint-*` 还能接着用

### 2.7 产物结构

```
/home/fanta/ft_outputs/ev-v1/
├── checkpoint-138/            # Trainer 中途存档（含优化器状态，很占空间）
├── lora_adapter/              # ← 只有这个是你需要的
│   ├── adapter_model.safetensors   # ~85MB（4B, r=16, 7 个模块）
│   ├── adapter_config.json         # 记录了底座路径 + r/alpha，加载时自动带上
│   ├── tokenizer.json / tokenizer_config.json
│   ├── chat_template.jinja
│   └── processor_config.json       # 多模态 Processor 配置
└── README.md                  # Trainer 自动生成的 model card
```

**只有 `lora_adapter/` 需要归档**，`checkpoint-*` 可以删。

### 2.8 常见报错

| 现象 | 原因 / 解法 |
|---|---|
| `SFTConfig` 没有这个参数 | TRL 版本旧。文件底部注释里有 `TrainingArguments` 的兼容写法，直接替换 |
| 训练刚开始就 CUDA OOM | `max_seq_length` 降到 1024；确认没别的进程占卡（`nvidia-smi`） |
| `PytorchStreamWriter failed writing file` | adapter 存到了 `/mnt/e`。改回 WSL 原生目录 |
| loss 一直是 0 或 nan | 检查 `apply_chat_template` 渲染出来是不是空 / `RESPONSES_ONLY` 把整条都 mask 了 |
| loss 不降（一直在 2.x 抖） | lr 太大或数据太同质；先 `--limit` 小样本验证数据渲染是否正确 |
| 训完加载报 shape mismatch | 用的不是同一个底座。`adapter_config.json` 里的 `base_model_name_or_path` 指向哪个就必须用哪个 |

### 2.9 数据量参考

| 场景 | 建议条数 | 说明 |
|---|---|---|
| 人设（E.V.） | 300~1000 条多轮 | ev-v1 361 / ev2 728 / ev3 797，够用。>2000 条收益递减 |
| 客服 | 200~500 条 | 重点是覆盖问题类型，不是堆量 |
| 通用指令（alpaca） | 51k | 只是拿来找手感，不是主目标 |

> 少而精 > 多而杂。人设数据里一条"助手腔"样本的破坏力，抵得上十条好样本。

## 三、`infer_lora.py` —— 最快的前后对比

**原理**：同一份权重，用 peft 的 `model.disable_adapter()` 临时关掉 LoRA 就是原始底座，
打开就是微调后 —— **一次加载，两种行为**，8GB 显存刚好够。

```bash
python infer_lora.py
ADAPTER=/home/fanta/ft_outputs/ev-v2/lora_adapter MAX_NEW=512 python infer_lora.py
DEBUG_PROMPT=1 python infer_lora.py     # 打印实际送进模型的文本（排查渲染问题）
```

- `PROMPTS` 是写死在脚本里的 4 道题（贴合度 / 解释 / 建议 / 创作），改题直接编辑文件
- 输出并排打印【微调前】【微调后】
- 局限：只有 4 题、不落盘、`disable_adapter` 不支持时会跳过前半段

**它适合"训完立刻看一眼"，不适合做决策** —— 要决策用下一个脚本。

## 四、`eval_persona.py` —— 人设评测

跑 `personas/haibara_eval.json` 里的**固定 25 题**（⚠️ 改了题集就失去版本间可比性），
自动标注肉眼容易漏的"崩人设"信号。

### 4.1 自动检查规则

| 规则 | 抓什么 |
|---|---|
| emoji | Unicode emoji 区段 |
| 网络流行语 | qwq/QAQ/orz/233/hhh/哈哈 / 绝绝子/yyds/破防/栓Q |
| AI 自曝 | "作为一个 AI / 人工智能 / 助手" |
| 助手腔 | "请问有什么可以帮您" |
| 感叹号 | `!` `！` |
| 可爱语气词 | `呀 啦 哒 哟 嘞` |
| 过长 | 回答 > 220 字 |

### 4.2 用法

```bash
# 微调前 vs 微调后（最常用）
python eval_persona.py --compare --adapter /home/fanta/ft_outputs/ev-v3/lora_adapter

# 再加一个上一版做三方对比：判断 v3 是不是真的比 v2 好
python eval_persona.py --compare \
    --adapter /home/fanta/ft_outputs/ev-v3/lora_adapter \
    --against /home/fanta/ft_outputs/ev-v2/lora_adapter

# 只跑底座（基线）
python eval_persona.py --base-only

# 把人设卡直接当 system 提示
python eval_persona.py --compare --adapter ... --system-file personas/haibara.md

# 只跑前 5 题（调试）
python eval_persona.py --adapter ... --limit 5
```

产出 `eval_result_<tag>.md`，Markdown 表格，可直接发给别人看。

### 4.3 报告怎么读

看**两个数**，不看单条回答：

1. **违规率**（有问题的条数 / 25）有没有下降
2. **平均回答长度**是不是更短了

`--against` 存在的意义：v3 的违规率可能比 v2 低，但长度变长了 —— 这种"指标好转、手感变差"的情况
只看单版报告看不出来。

### 4.4 为什么是串行加载

8GB 显存塞不下两个 4B，所以脚本对每个模型 `load → 跑完 → del → torch.cuda.empty_cache()`，
**一次只驻一个**。跑三方对比要加载三次，慢是正常的。

## 五、`chat_lora.py` —— 终端多轮对话

唯一的**流式**入口：`TextIteratorStreamer` + 独立线程生成，主线程逐字打印，
并且实时扫描 `STOP_MARKS`，一旦模型开始编下一轮就立刻切断。

```bash
python chat_lora.py
ADAPTER=/mnt/e/VMOS_workspace/model_tuning/models/Qwen3.5-4B python chat_lora.py   # 跑底座
SYSTEM="你是 E.V.，回答极短。" KEEP_TURNS=4 python chat_lora.py
```

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `ADAPTER` | `.../qwen35-4b-lora/lora_adapter` | 填底座目录就退化成原始模型 |
| `MAX_NEW` | 512 | 单轮最多生成多少 token |
| `TEMPERATURE` / `TOP_P` | 0.7 / 0.9 | 人设对话别调太高，容易跑偏 |
| `SYSTEM` | 空 | 环境变量人设 |
| `KEEP_TURNS` | 8 | 只带最近 8 轮历史，防止上下文爆 |
| `MEMORY_MD` | 同目录 `memory.md` | 外挂记忆文件路径 |

会话内命令：

```
/reset            清空上下文（长期记忆不受影响）
/remember 我住在杭州   记一条（写入 memory.md，立即生效）
/memory           查看全部记忆
/forget 杭州       删一条
/exit             退出
```

### 关键设计：system 每轮现拼

```python
def build_system():
    parts = [SYSTEM] + [mem.as_prompt_block()]   # 每轮重新读文件
```

所以**手改 `memory.md` 后下一句话就生效，不用重启、不用重训**。
`history` 里只存 user/assistant，system 不落历史 —— 不会被 `trim()` 截掉。

## 六、`memory.py` —— 外挂长期记忆

核心理念一句话：**记忆靠文件，风格靠微调。加记忆不需要重新训练。**

### 6.1 为什么用 Markdown 而不是 JSON

- 人可读：打开 VSCode 就能改，不用管引号和逗号
- 模型喜欢：标题 + 列表就是它训练时的母语
- 代价：没有严格结构，所以约定极简 —— **一条一行，以 `- ` 开头**
- 需要给程序读的结构化数据才用 JSON，两者可以并存

### 6.2 文件格式

```markdown
# 长期记忆

## 关于我
- 我叫 fanta，做后端开发

## 偏好
- 回答尽量简洁

## 记忆条目
- 我住在杭州  <!-- 2026-10-11 -->
```

`<!-- 日期 -->` 是时间戳注释，`list()` 会去掉。

### 6.3 API

```python
from memory import Memory
mem = Memory("memory.md")
mem.remember("我住在杭州")   # 追加，已存在返回 False（自动去重）
mem.forget("杭州")           # 删第一条含关键词的，返回被删内容
mem.list()                   # 所有条目（纯文本，无时间戳）
mem.as_prompt_block()        # 拼成 system 提示块；没记忆返回空串
```

命令行自测：

```bash
python memory.py add 我住在杭州
python memory.py list
python memory.py forget 杭州
python memory.py prompt
```

### 6.4 局限（别指望它太多）

- 纯字符串匹配，**没有向量检索**，条目多了只能靠"越靠前越重要"
- 全部记忆直接拼进 system，**每条都在烧上下文**
- 只适合"我叫什么、我住哪、别叫我全名"这类**稳定事实**，不适合记对话流水

## 七、`check_model.py` —— 30 秒分诊

### 为什么需要它

llama.cpp / GGUF 对 Qwen3.5 这种**混合注意力 + MTP** 架构支持有偏差，输出会是
"有语法没语义"的字词汤。这时最大的时间黑洞是：**分不清是模型坏了还是后端坏了**。

本脚本用**和评测完全相同的加载方式**跑 3 句话，输出三样东西用于判断：

| 看什么 | 正常应该是什么 |
|---|---|
| `prompt 尾部` | 能看到 `<|im_start|>assistant` —— 模板渲染对了 |
| `tok/s` | 4bit GPU 20~40；个位数说明跑在 CPU 上 |
| `回答` | 十几字、冷淡、带省略号；字词汤则看「逐 token 解码」 |

```bash
python check_model.py                       # 测 ev-v2（默认）
python check_model.py --base                # 只测底座，排除 adapter 的锅
python check_model.py --no-system           # 不带 system，看是不是提示词的锅
python check_model.py --adapter /path/to/lora_adapter
python check_model.py --max-new 200 --temp 0
```

**排查顺序**：`--base` 正常但加 adapter 乱 → 问题在 adapter；`--base` 也乱 → 模型或环境问题。

## 八、`serve_hf.py` —— OpenAI 兼容服务

### 为什么需要它

`llama.cpp` 编的是 **CPU 版**，4B 只有 3~8 tok/s，语音对话根本没法用；
重编 CUDA 版要装 3GB CUDA Toolkit。而 `~/venvs/ft` 里已经有 torch + CUDA + Unsloth，
所以直接用 PyTorch 在 GPU 上跑，对外暴露**和 llama-server 一模一样的接口**。

| | llama.cpp (CUDA 版) | `serve_hf.py` (PyTorch) |
|---|---|---|
| 显存 | ~2.6GB (Q4) | ~4GB (4bit) |
| 速度 | 最快 | 够用（20~40 tok/s） |
| 启动 | 秒开 | 30~60 秒 |
| 需要编译 | ✅ 要 CUDA Toolkit | ❌ 不需要 |

```bash
source ~/venvs/ft/bin/activate
python serve_hf.py --adapter /home/fanta/ft_outputs/ev-v2/lora_adapter
python serve_hf.py --base --port 8081          # 跑底座
```

验证：

```bash
curl http://127.0.0.1:8080/v1/models
curl http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"ev","messages":[{"role":"user","content":"我今天很累"}]}'
```

### 实现要点

- 手写 `http.server.ThreadingHTTPServer`，**没有 FastAPI 依赖**，只实现两个端点：
  `/v1/models`、`/v1/chat/completions`
- 请求里**没有 system 就自动注入内置的 `SYSTEM`**（人设兜底）；有 system 就尊重调用方
- `max_tokens` 上限硬截 512
- 每轮打印 `[生成] n tokens / x.x s = y tok/s`，方便判断性能

### 局限

- 多个请求同时来会**抢同一份 GPU 状态**，实际是串行甚至 OOM。单人语音助手够用，别当生产服务器
- 没有 auth、没有流式（`stream` 参数会被忽略）
- 换成 llama.cpp CUDA 版时，调用方只改 `LLM_BASE`，**一行代码不用动**

接 P1 语音助手：

```bash
LLM_BASE=http://127.0.0.1:8080/v1 bash run_app.sh
```

## 九、`export_gguf.py` —— 合并 / 导出 GGUF（当前别用）

```bash
# 完整导出（首次会自动下载并编译 llama.cpp，十几分钟）
python export_gguf.py --adapter /home/.../lora_adapter --out ~/gguf/ev

# 只合并成 HF 格式，不碰 llama.cpp、不联网
python export_gguf.py --adapter /home/.../lora_adapter --out ~/gguf/ev-merged --merged-only
```

| 模式 | 做什么 | 需要 |
|---|---|---|
| 默认 | LoRA 合并 + 量化成 GGUF | llama.cpp + 联网 |
| `--merged-only` | 只合并成 16bit HF 完整模型 | 都不需要 |

导出后是"合并完的完整模型"，之后不再需要 adapter；`q4_k_m` 体积/质量最平衡（4B 约 2.5GB）。

### ⚠️ 现状：qwen3.5 混合架构下输出乱码，已弃用

这不是参数问题，是 llama.cpp 对该架构支持不完整。**目前日常使用走两条路**：

- 开发调试 → `chat_lora.py`
- 提供服务 → `serve_hf.py`

不要在 GGUF 上继续耗时间，`check_model.py` 就是为确认这件事写的。

## 十、`run_chat.sh` —— 9B GGUF 聊天服务

注意：**它跑的是 9B 底座，不是你的 LoRA**。作用是"有个能聊的本地模型"，和人设微调是两条线。

```bash
bash run_chat.sh                        # 16k 上下文
CTX=32768 bash run_chat.sh              # 更长上下文（8GB 会吃紧）
ENABLE_VISION=1 bash run_chat.sh        # 启用看图（多占约 900MB）
MODEL=/path/to/x.gguf bash run_chat.sh  # 换模型
```

| 变量 | 默认 | 说明 |
|---|---|---|
| `CTX` | 16384 | 8GB 建议 8192~16384 |
| `NGL` | 99 | 全部层上 GPU；爆显存往下调（如 32） |
| `PORT` | 8080 | 自带 Web UI + `/v1` |
| `ENABLE_VISION` | 0 | 1 时挂 `mmproj-F16.gguf` |

脚本会先检查模型文件和 `llama-server` 是否存在，缺了就打印编译命令 —— **不用猜为什么起不来**。

## 十二、速查表

```bash
# 训练
SMOKE_TEST=0 NUM_EPOCHS=5 OUTPUT_DIR=... python train_lora.py

# 对比
python infer_lora.py
python eval_persona.py --compare --adapter ... [--against ...]

# 对话
python chat_lora.py
python serve_hf.py --adapter ...

# 诊断
python check_model.py [--base] [--no-system]

# 环境
source ~/venvs/ft/bin/activate
nvidia-smi
```

| 症状 | 先查 |
|---|---|
| 训不起来 / OOM | `MAX_SEQ_LEN` 降到 1024、`nvidia-smi` 有无别的进程 |
| 训完还是助手腔 | 数据里有没有助手腔样本、`RESPONSES_ONLY` 开没开、system 提示 |
| 回答超长 / 停不下来 | `MAX_NEW`、数据里的长样本、`STOP_MARKS` |
| 输出乱码 | `check_model.py` —— 大概率是 GGUF 后端，不是模型 |
| 速度个位数 tok/s | 跑在 CPU 上，检查 `torch.cuda.is_available()` |
| adapter 加载后行为没变 | `ADAPTER` 路径是否指到 `lora_adapter` 目录（不是 `checkpoint-*`） |
