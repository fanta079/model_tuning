# 参考项目调研（2026-10-23）

目标：给 E.V. 的「实时语音」找可抄的作业。当前瓶颈已知——
TTS 本地 RTF≈4（换云端后解决），剩下 **VAD 判停 0.85s + ASR + 首字 0.85s**。

按「能直接拿来用」排序，不按 star 排。

---

## 一、直接对标：百聆（bailing）—— 同一套架构，时延 800ms

[wwbin2017/bailing](https://github.com/wwbin2017/bailing) · 1785★ · Python · 2026-04 仍活跃

> ASR + VAD + LLM + TTS 的语音对话机器人，端到端 **800ms**，**无需 GPU**，
> 支持打断、记忆、工具调用。中文项目，文档齐全。

它的栈和我们几乎一样（edge-tts 也在里面），但有两处关键差异：

### 1) VAD 用的是神经网络，不是音量阈值 ⭐ 最值得抄

```yaml
VAD:
  SileroVAD:
    threshold: 0.5
    min_silence_duration_ms: 200      # 停 200ms 就判定说完了
```

**200ms，而我们是 850ms。** 这不是他们敢调、我们不敢调——是判据不同：

| | 我们（`app/index.html`） | 百聆 |
|---|---|---|
| 判据 | 音量 RMS > 0.055 / 0.10 | Silero VAD 输出「这是人声」的概率 |
| 为什么留 0.85s 余量 | 音量阈值会把换气、环境噪声误判成说话，只能靠长静音兜底 | 模型直接判语音结束，不需要长兜底 |

这条能白捡 **0.5~0.6 秒**，而且是每回合都省。Silero VAD 是 ONNX，1ms 级，
浏览器端有 onnxruntime-web 的现成用法，服务端也有 Python 版。

### 2) ASR 用 SenseVoiceSmall，不是 whisper

非自回归、中文优化、自带标点，比 whisper-large-v3 快一个量级。
whisper 是自回归解码，长音频会线性变慢；SenseVoice 是一次前向。

### 3) 打断用「播放器 × 说话」二维状态表

| 播放器 | 用户在说话 | 处理 |
|---|---|---|
| 播放中 | 否 | 正常 |
| 播放中 | **是** | **打断** |
| 未播放 | 否 | 正常 |
| 未播放 | 是 | VAD → ASR |

我们现在是分散在 `loop()` 里的 if 判断，语义等价但不好读。可以照这个表重写。

## 二、低延迟 TTS：想同时保住「她的嗓子」和「快」

现状：Qwen3-TTS 0.6B 克隆音色对，但 RTF≈4，无流式生成（源码里
`non_streaming_mode` 只是模拟流式文本输入）。要两者兼得只能换模型。

| 项目 | 首包 | 音色 | 备注 |
|---|---|---|---|
| [FunAudioLLM/CosyVoice](https://github.com/FunAudioLLM/CosyVoice) | **150ms** | 零样本克隆（3~10s 参考） | 双向流式（文本进、音频出），官方阿里，有 kv cache + sdpa 优化 |
| [Lucas1479/Aqua-TTS](https://github.com/Lucas1479/Aqua-TTS) | **213~307ms** | GPT-SoVITS 角色音色 | 明确写着「built for low-latency voice conversation with your **LoRA characters**」 |
| [herimor/voxtream](https://github.com/herimor/voxtream) | **74ms** | 零样本 | 全流式，4× 实时；偏研究，工程成熟度低 |
| [remsky/Kokoro-FastAPI](https://github.com/remsky/Kokoro-FastAPI) | 低 | ❌ 无克隆 | 82M，快、稳，但只能用它自带音色 |
| [2noise/ChatTTS](https://github.com/2noise/ChatTTS) | 中 | 音色随机 | 39.9k★，但不可控、非商用协议 |

**结论**：CosyVoice2 是唯一「150ms + 可克隆 + 中文」三样都占的。
我们已有的 `ref.wav`（9.7s）可以直接当它的 zero-shot 参考，不需要重新造音色。
备选是 Aqua-TTS——如果我们以后改用 GPT-SoVITS 家族。

## 三、工业级框架：如果想重构整条链路

| 项目 | ★ | 说明 |
|---|---|---|
| [pipecat-ai/pipecat](https://github.com/pipecat-ai/pipecat) | 16.7k | 帧（frame）式 pipeline，VAD/打断/中断处理都是现成的 |
| [livekit/agents](https://github.com/livekit/agents) | 14.9k | 同上，配套 WebRTC，天然解决手机端延迟 |
| [TEN-framework/TEN-Agent](https://github.com/TEN-framework/TEN-Agent) | 11.2k | 国产，可视化编排，支持全双工 |

这三个的价值不在代码，而在**架构参考**：它们把「语音 agent」拆成
`transport → VAD → ASR → LLM → TTS → transport` 的帧流，打断就是往流里插一个
控制帧。我们现在的 `turn_stream` 是等价的简化版，够用；真要上全双工再考虑。

⚠️ 不建议现在迁移——我们只有一个人用、一条链路，引入框架的复杂度大于收益。

## 五、给 E.V. 的三步（按性价比）

1. **换 VAD → silero-vad**：判停 850ms → 250~300ms。
   改动小（前端 or 服务端二选一），收益 0.5s+/回合，且能明显减少「说一半被切」。
2. **换 ASR → SenseVoiceSmall**：中文更准、更快、带标点。
   先 A/B 测：同一段音频，比 whisper-large-v3 的耗时和错字率。
3. **换 TTS → CosyVoice2 双向流式**：只有它能同时给「150ms」和「她的嗓子」。
   工作量最大（新 venv + 新服务 + 前端 PCM 流式播放），但这是唯一能进 1 秒级的路。

做完 1+2，「说完话 → 开始说话」大概能从 2.6s 压到 **1.5s 左右**；
再加上 3，能进 **1 秒内**。
