# 人设数据生产指南

> 目标：从一个「人设卡」出发，造出可训练的数据，训出能**稳定扮演**该人设的模型。
> 本文以 `personas/haibara.md` 为例（角色名 **E.V.**，性格取自《名侦探柯南》的灰原哀）。

---

## 〇、全景

```
人设卡 (personas/*.md)        ← 约束"像不像"
        ↓
场景矩阵 (personas/*_scenes.json)  ← 决定"多不多样"
        ↓
gen_persona_data.py  →  my_data/xxx.json
        ↓  prepare_data.py
train.json / val.json
        ↓  train_lora.py
lora_adapter
        ↓  eval_persona.py      ← 对比微调前后
        ↓  export_gguf.py       ← 可选，日常用 llama.cpp 跑
```

**三件套缺一不可**：人设卡 **防 OOC**、场景矩阵 **保多样性**、种子样本 **定手感**。
只做其中一个，出来的数据都是废的。

---

## 一、人设卡：先写"不能做什么"

`personas/haibara.md` 的结构可以直接照搬，五个要点：

1. **称呼设定放最前面，标注「最高优先级」**
   称呼是最容易错的地方，而且错了整批数据都废。

2. **写清"什么时候用"，不只是"用哪个词"**
   > 默认只用「你」，**大约每 10 条回答里有 1 条**会叫「Fanta」
   > —— 全是就廉价了，一条不叫又失去了那份分量

   比例要写成模型能执行的具体数，别写"偶尔"。

3. **底线用 ❌ 逐条列出**
   不用 emoji、不用「呀啦哒哟」、不写小作文、不说"有什么可以帮您"……

4. **给 6~8 条风格锚点**
   让模型知道"要多短、多冷"。这些锚点的质量决定整批数据的质量。

5. **附一组「正确 vs 错误」对照表**
   对比比描述有效得多。

> **写法的核心**：先写死"不能做什么"，再写"要做什么"。只写正面描述，模型很容易滑回通用助手腔。

---

## 二、场景矩阵：多样性靠结构，不靠祈祷

维度设计（`personas/haibara_scenes.json`）：

```
角色状态 × 场景 × 语气 × 长度 × 轮数 × 称呼  ≈  18000 种组合
```

### ⚠️ 踩过的两个坑

**坑 1：一次调用只给一个场景 → 全批同质**

第一次实测：一次调用生成 6 条，结果**6 条全是同一个场景**（只是换了说法）。
修法：**一次调用下发 N 个不同任务**，prompt 里要求"第 i 条对应任务 i，场景必须真正不同"。

**坑 2：比例靠 prompt 措辞不可靠**

人设卡里写"约 10% 会叫名字"，实测生成 240 条 —— **叫名字 0 条**。
模型把"稀有"理解成了"基本不用"。

修法：**把比例做成一个维度**，而不是一段描述：

```json
"call_names": [
  "只用「你」，不叫名字",   // ×9
  ...
  "必须叫一次名字「Fanta」（郑重 / 心疼 / 生气的时刻）"   // ×1
]
```

这样 9:1 的比例由**结构**保证，不依赖模型的理解。**任何"比例型"要求都该这么做。**

## 三、生成：种子锚定

```bash
export OPENAI_API_KEY=sk-xxxx
python gen_persona_data.py \
    --api-base https://api.deepseek.com/v1 --model deepseek-chat \
    --seed-file my_data/ev_manual_40.json --num-seeds 20 \
    --n 360 --per-call 12 --out my_data/ev_api.json
```

| 参数 | 作用 |
|---|---|
| `--seed-file` | **把新手写精品当 few-shot 锚点** —— 比纯生成质量高一截 |
| `--num-seeds` | 送进提示词的种子条数；给了 seed-file 可以调到 20~30 |
| `--per-call` | 一次生成几条（每条对应一个不同任务）|
| `--dry-run` | **先看提示词，不花钱** |
| `--num-seeds` / `--sleep` | 控制 token 量与请求频率 |

**每批落盘 + 断点续传**：中断了直接重跑同一条命令，已生成的自动跳过。
**规则质检**自动拦：emoji / 网络流行语 / AI 自曝 / 助手腔 / 超长。

### 推荐配比：手写 10% + 机造 90%

手写的几十上百条是**标杆**（也是 few-shot 种子），机造的负责铺量。
单纯靠机造，手感会飘；单纯靠手写，产量不够。

---

## 四、体检：生成完先统计，再训练

**别跳过这步。** 花 10 秒统计能省几小时训练：

| 指标 | 健康值 | 说明 |
|---|---|---|
| assistant 回复重复率 | **< 15%** | 高了说明场景没打散 |
| 平均回复长度 | 与人设匹配 | 灰原哀该在 20 字上下 |
| 违规数 | **0** | emoji / 感叹号 / 可爱语气词 |
| 关键特征比例 | 符合设计 | 如"叫名字"占比 |

> 实测记录（400 条）：重复率 **2.6%**、平均 **18 字**、违规 **0**、叫名字 **6.6%** —— 达标。

## 五、数据量参考

| 条数 | 效果 |
|---|---|
| < 100 | 只能验证流程跑通 |
| **300 ~ 500** | 能明显看出人设 |
| 800 ~ 1500 | 比较稳，长期用够 |
| > 3000 | 边际收益下降，**该把精力转回人设卡** |

## 六、训练

```bash
source ~/venvs/ft/bin/activate
DATA_PATH=/mnt/e/VMOS_workspace/model_tuning/my_data/ev/train.json \
DATA_FORMAT=chat RESPONSES_ONLY=1 NUM_EPOCHS=5 \
OUTPUT_DIR=/home/fanta/ft_outputs/ev-v1 \
SMOKE_TEST=0 python train_lora.py
```

- **不加 `SYSTEM`** —— 训练数据里没有 system 消息，加了反而不一致
- 361 条 × 5 轮 ≈ 225 步，8GB 上约 **15~30 分钟**
- `OUTPUT_DIR` 每次换版本号（`ev-v1` / `ev-v2`），别覆盖，训崩了能回滚

## 八、迭代闭环

```
训练 v1 → 听声音 / 看评测 → 定位"不像"的具体场景
        → 回写人设卡（或补场景、补种子）
        → 重新生成 → v2
```

**核心经验：改人设卡比加数据便宜得多。**
先改卡，再考虑加量。人设卡改对了，同样的数据量效果能差一个档次。

## 九、实战案例：v1 全程数据

第一版（`ev-v1`）的完整记录，可作为**基线参照**。

### 数据

| 项 | 值 |
|---|---|
| 手写种子 | 40 条 |
| API 生成 | 360 条（`--seed-file` 用上面 40 条当锚点）|
| 清洗后 | **361 train / 19 val** |
| 体检 | 回复重复率 2.6%｜平均 18 字｜违规 0｜叫名字 6.6% ✅ |

### 训练

| 项 | 值 |
|---|---|
| 模型 | Qwen3.5-4B + QLoRA |
| 参数 | `NUM_EPOCHS=3`、batch 1 × 累积 8 |
| 步数 | **138**（= 361÷8×3）|
| loss | **3.79 → 0.79**（step 100 处陡降，风格在此"接通"）|
| 耗时 | 约 10 分钟 |

### 评测结果（25 题固定题集）

| | 微调前（底座）| 微调后（+LoRA）|
|---|---|---|
| 违规 | 24/25（96%）| **0/25（0%）** |
| 平均长度 | 269 字 | **18 字** |

底座每条都在"作为一个人工智能…"+ emoji + 小作文；微调后这些全消失，长度降到 18 字。

**出彩样例**

```
你脸色不太好，是不是没睡好？   → Fanta。我昨晚熬到三点。现在这样还勉强够用。
谢谢你这段时间照顾我。        → ……别说得像告别一样。我又没做什么。
这件衣服很适合你，真可爱！     → ……嗯。是你上次说喜欢的那种，我留的。
有人在你面前哭，你会怎么办？   → 递纸巾。别的别管。
你觉得活着有意思吗？          → ……还行。
```

> 注意第 1 条：**叫名字出现在"关心场景"**，正是设计意图（名字 = 郑重时刻）。
> 说明模型学到的是**规律**，不只是"偶尔加个词"。

### 暴露的问题 → v2 修法

| v1 的问题 | 样例 | v2 对应的修法 |
|---|---|---|
| **人设反了**：答应得过于轻快 | 「**去去去**。别指望我带着什么好吃的。」| 人设卡加底线：「即使同意也是冷淡地同意，说「……行。」不说「去去去」「好呀」」|
| **拼凑感**：语义不清 | 「……看脸不行。」| 数据量 400 → 800~1000，减少拼接 |
| **网感用词** | 「其实挺**缺爱**的。」| 人设卡加底线：「不用现代心理学/网络词汇（缺爱/内耗/边界感）」|
| **鸡汤腔** | 「不如把时间花在**刀刃上**。」| 人设卡加底线：「不给人生建议、不说大道理」|
| **答非所问** | 问"变回原来的样子"→「先睡够三小时再说」| 人设卡质检加第 4 问 + 生成器 prompt 加「必须切题」|
| **回避失效** | 问「那个药」→「说明书在盒子上」（当成普通药了）| 人设卡新增「**回避规则**」+ 场景矩阵补 5 条回避类场景 |

### 关键收获

1. **训练前的体检有用** —— 6.6% 的叫名字比例，在评测里兑现成了"位置准确的一次叫名字"
2. **规则合规 ≠ 真的像** —— 微调后 0 违规，但仍有 5 条"不像"。规则只能拦硬伤，语气要靠人读
3. **问题的根因几乎都在数据侧** —— v2 修的 6 个问题里，5 个是改人设卡/场景矩阵，只有 1 个是加数据量
4. **改人设卡比加数据便宜** —— 先改卡，再考虑加量

### v2 → v3：把「回避」从全局策略降级为**场景属性**

v2 修好了"回避失效"，但**修过头了**。上线实测：

```
你：你是谁？
她：……你问这个做什么。

你：我是谁
她：……你问这个，是想让我答，还是想让我问。
```

25 题固定评测里，「你问这个做什么」出现了 **6 次（24%）**，其中 #1 和 #5 的回答**一字不差**。
这是模型把「回避」学成了一个**通用策略**：凡是问到关于她自己的事，就反问。

**根因不是比例，是措辞的强度。**

| 版本 | 写法 | 结果 |
|---|---|---|
| v1 | 「**大约每 10 条**会叫一次名字」| 太弱 → 实际生成 **0 条** |
| v2 | 「触及药/组织时**必须**回避」| 太强 → 泛化成**万能句** |

两次都指向同一条规律：**模糊的强度描述不可控，必须落到结构上。**

**v3 的修法（三处，全在配置层，不用改代码逻辑）**

1. **人设卡加「边界」**：回避只针对触发词列表；被问「你是谁」直接答 E.V.；
   **反问一场对话最多一次**；给出正误对照：「E.V.。……就这么叫我。」vs「你问这个做什么。」
2. **场景矩阵加两条身份自述场景**（你是谁 / 我是谁），并标注"必须直接答"
3. **回答策略与场景强绑定**（`sample_task()` 里判断）：
   - 场景命中触发词 → `可以回避或反问`
   - 否则 → `正面回答，不许回避`
   
   这样**不会出现「那个药」配「正面回答」的自相矛盾任务书** —— 这是随手改成"80% 正面"最容易犯的错。

改完的统计：场景 33 → **36**，触及过去的占 **13.8%**，配对错误 **0**。

> **一条可复用的经验**：凡是"某类回答应该占多少比例"的要求，
> 都不要写成 prompt 里的一句话，而要写成**场景 / 维度 / 分支**。
> 模型不理解"约 10%"，但它会严格执行"这个场景对应这个策略"。

## 附：手写 vs 机造

| | 手写 | 机造 |
|---|---|---|
| 质量 | 高 | 中 |
| 产量 | 低（每轮几十条）| 高（几分钟几百条）|
| 成本 | 0 | 几块钱 |
| **用法** | **当种子 + 当标杆** | **铺量** |

最佳组合：**手写 40~100 条当 seed → API 按这个手感铺到几百条**。
